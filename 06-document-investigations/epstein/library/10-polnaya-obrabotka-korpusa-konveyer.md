# 10 — Полная обработка корпуса: конвейер

> Задача: обработать **100% файлов** Epstein Library. Это выполнимо — но как инженерный проект на твоей машине, а не как чтение в чате. Здесь: почему, архитектура, код, оценки времени/денег, протокол совместной работы и критерий «обработали всё».

---

## 0. Арифметика, которую не обойти

- Опубликовано ≈ **3,5 млн страниц** (+2000 видео, +180 тыс. изображений); один Data Set 1 — ~3,1 тыс. PDF, датасетов 12, и файл ≠ страница (один EFTA-PDF бывает на сотни страниц).
- 3,5 млн страниц × ~400 токенов ≈ **~1,4 млрд токенов**. Контекст одной сессии Claude — порядка сотен тысяч токенов. Разрыв — **четыре порядка**: корпус физически не помещается ни в один чат, сколько бы заходов ни было.
- Сетевой доступ моего sandbox к justice.gov закрыт (белый список доменов), web_fetch — поштучный и лимитированный: «скачать всё чатом» — недели вызовов с нулевым удержанием в памяти.
- Вывод: «все файлы» обрабатывает **машина** (скачка, OCR, индекс, NER — 100% покрытие), а интеллект (мой и твой) тратится на **запросы к обработанному** и разбор приоритетных кластеров. Ровно так корпус обработали те, кто реально это сделал (независимая база EpsteinExposed: один инженер, >2 млн документов в индексе).

## 1. Архитектура

```
[1 манифест] → [2 скачивание + sha256] → [3 OCR] → [4 FTS-индекс]
     → [5 NER-имена] → [6 LLM-слой по кластерам] → [7 батч-разбор с Claude]
```
Этапы 1–5 — тотальные (100% файлов). Этапы 6–7 — по приоритетным очередям, потому что тотальный LLM-прогон бессмыслен по деньгам и не нужен по смыслу (см. §6).

## 2. Этап 1 — манифест (сегодня, ~10–20 мин)

```bash
pip install requests beautifulsoup4
python efta_manifest.py --out ./manifest
```
Выход: `manifest.csv` (каждый файл каждого датасета), `counts.csv` (**точное** число файлов по всем 12 датасетам — ответ на «и это всё?» цифрами, а не прикидкой), `aria2_input.txt` (готовый вход для скачивания), `bates_gaps.txt` (пропуски нумерации = документы, отозванные на редактуру, — их перечень сам по себе исследовательский результат: это карта того, что DOJ трогал после публикации).

## 3. Этап 2 — скачивание и целостность

```bash
aria2c -i manifest/aria2_input.txt -j 4 --max-tries=5 --retry-wait=10 \
       --auto-file-renaming=false --conditional-get=true
find corpus -name '*.pdf' -exec sha256sum {} + > SHA256SUMS-$(date +%F).txt
```
Оценка: объём PDF-массива покажет сам процесс (сотни ГБ вместе с медиа; чистые PDF заметно меньше). При 100 Мбит/с: 100 ГБ ≈ 2,5 ч, 300 ГБ ≈ 7–8 ч. Диск планируй с запасом ×2 (OCR-копии). Видео/изображения — отдельным манифестом позже: их обработка иная (метаданные + выборочный просмотр, не OCR).

## 4. Этап 3 — OCR (тотально, фоном)

```bash
find corpus -name '*.pdf' | parallel -j 8 \
  ocrmypdf --skip-text --optimize 0 --output-type pdf {} {}
```
(или очередь на Python с multiprocessing; `--skip-text` не трогает уже текстовые PDF). Формула времени: `страницы / (процессы × 1–3 стр/с)`. Для 3,5 млн стр. на 8 процессах ≈ **2–6 суток фонового счёта** — это и есть твоё «неважно сколько времени»: время тратит Mac, не ты. Рукописи Tesseract берёт плохо — они всплывут флагом на этапе 4.

## 5. Этап 4 — тотальный индекс и поиск

```bash
pip install pymupdf
python efta_index.py build  --corpus ./corpus --db efta.db
python efta_index.py stats  --db efta.db
python efta_index.py search --db efta.db --query '"wire transfer"'
```
После этого **каждый** файл корпуса отвечает на запросы за миллисекунды. `needs_ocr=1` — очередь на до-распознавание (прогнал ocrmypdf → повторный `build` переиндексирует только изменённое). Это момент, когда «обработали все файлы» перестаёт быть лозунгом: любой документ находится и читается по требованию.

## 6. Этапы 5–6 — имена и LLM-слой

- **NER (100% текста):** конвейер из файла 08 §9 (spaCy PERSON → нормализация → частоты → ручная верификация топа). Выход — твоя собственная поимённая база по всему корпусу.
- **LLM-слой (по кластерам):** тотальный прогон = `1,4 млрд ток. × тариф`; даже при $0,2/1M это ~$280 только на вход — и 95% уйдёт на дубликаты, бланки и мусор. Правильно: FTS/NER-фильтрами режем корпус на очереди и гоним через твои BYOK-ключи (DeepSeek/Qwen/OpenRouter) только осмысленное — обычно 3–10% корпуса, т.е. **$10–40 за очередь**. Смета всегда: `(ток_вход × цена_вход + ток_выход × цена_выход)`.
- Приоритетные очереди: 1) переписка/e-mail; 2) FD-302; 3) grand jury; 4) финансовые записи; 5) BOP/материалы смерти; 6) остаток по требованию.

## 7. Этап 7 — протокол батч-работы со мной

1. Ты присылаешь батч: до ~100–150 страниц текста (или выжимки LLM-слоя + спорные документы целиком) + указание очереди.
2. Я возвращаю: разбор по существу, имена+роли+статусы, красные флаги, привязку к делам и файлам библиотеки (01–09), что копать следующим.
3. Прогресс ведём в `PROGRESS.md` в твоём вахтенном стиле:
```markdown
## Очередь 1 — переписка
- [x] batch-001 EFTA00000001–00000420 · находки: … · спорное: …
- [ ] batch-002 …
```
4. Заходов — сколько потребуется. Ограничение всегда одно: в чат заходит батч, а не корпус.

## 8. Критерий «обработали ВСЕ» (Definition of Done)

- [ ] 100% файлов в манифесте; пропуски Bates зафиксированы и мониторятся повторным прогоном манифеста;
- [ ] 100% скачано, sha256 сняты, снимок датирован;
- [ ] 100% через OCR; `needs_ocr` → 0 (или остаток помечен «рукопись, ручной просмотр»);
- [ ] 100% в FTS-индексе; `stats` сходится с манифестом;
- [ ] 100% текста через NER; поимённая база собрана и верифицируется;
- [ ] приоритетные очереди 1–5 пройдены через LLM-слой и батч-разборы;
- [ ] остаток корпуса доступен поиску по требованию — и это осознанный стандарт, а не недоделка: «обработано» = каждый файл проглочен машиной и отвечает на запросы, а не «каждый прочитан глазами» (глазами 3,5 млн страниц не читал никто на планете, включая DOJ — у них на это ушло 500+ юристов и то поштучно).
