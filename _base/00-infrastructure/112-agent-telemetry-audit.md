## §2. Структура записи — что именно сохраняется перед отправкой

Снято с живого лога текущей сессии. Типы записей в одном файле:

```
user 172 · assistant 349 · attachment 633 · system 18 · file-history-snapshot 10
file-history-delta 19 · queue-operation 24 · mode/agent-name/custom-title 77 каждая
```

Поля верхнего уровня (71 штука). 🔴 Наиболее говорящие из них:

| Поле | Что несёт |
|---|---|
| `message.content` | **сам текст**: промпт владельца, ответ модели, результаты инструментов |
| `attachment` | 🔴 **633 записи за сессию** — вложения контекста: содержимое прочитанных файлов, вывод команд, системные напоминания |
| `toolUseResult` | что вернул инструмент: вывод `Bash`, текст файла из `Read` |
| `wireIngestContext`, `wireToolInputs` | то, что ушло «на провод» — входы инструментов в отправленном виде |
| `cwd`, `gitBranch` | рабочий каталог и ветка |
| `serverClassifierRequest`, `serverClassifierContext` | обращения к серверному классификатору разрешений |
| `usage.inference_geo` | 🔴 регион инференса, приходит **в ответе** |
| `permissionMode`, `effort`, `model` | режим, усилие, модель |
| `requestId`, `sessionId`, `uuid`, `timestamp` | идентификаторы для сопоставления с логом |

**Скелет записи `assistant`** (значения заменены на тип и длину):

```
message: { model, id, role, content[], stop_reason,
           usage: { input_tokens, cache_creation_input_tokens,
                    cache_read_input_tokens, output_tokens,
                    output_tokens_details.thinking_tokens,
                    server_tool_use.{web_search_requests, web_fetch_requests},
                    service_tier, cache_creation.{ephemeral_1h, ephemeral_5m},
                    inference_geo, speed } }
requestId, apiBlockIndex, sessionId, cwd, gitBranch, timestamp, version
```

**Воспроизвести этот разбор** (печатает структуру, НЕ содержимое):

```bash
python3 - <<'PY'
import json, collections, pathlib
d = pathlib.Path.home()/".claude/projects/-Users-vasyaevdokimov-repos-base-repo"
f = max(d.glob("*.jsonl"), key=lambda p: p.stat().st_mtime)
c = collections.Counter()
for line in f.read_text(errors="replace").splitlines():
    try: c[json.loads(line).get("type","?")] += 1
    except Exception: pass
print(f.name, f"{f.stat().st_size/1048576:.1f} МБ", dict(c))
PY
```

## §3. Как запускать `claude-xray.sh`

Скрипт — `mission-control/scripts/claude-xray.sh`, уже исполняемый.

```bash
cd ~/repos/<любая репа>
~/repos/mission-control/scripts/claude-xray.sh              # все категории
~/repos/mission-control/scripts/claude-xray.sh api          # только сеть
~/repos/mission-control/scripts/claude-xray.sh 'api,hooks'  # несколько
~/repos/mission-control/scripts/claude-xray.sh '!1p,!file'  # всё, кроме названных
XRAY_KEEP=1 ~/repos/mission-control/scripts/claude-xray.sh  # дописывать, не начинать заново
```

Лог: `~/Documents/NOT FOR CLAUDE/claude-debug-session.log`.
Прошлый прогон переименовывается в `…log.ГГГГММДД-ЧЧММСС.bak`, если не задан
`XRAY_KEEP=1`.

**Флаги, на которых он построен** — настоящие, сверены с `claude --help`
версии 2.1.284:

| Флаг | Что делает |
|---|---|
| `-d, --debug [filter]` | режим отладки с фильтром категорий (`api,hooks`, отрицание `!1p,!file`) |
| `--debug-file <path>` | писать отладку в файл; **сам включает режим отладки** |
| `--verbose` | подробный вывод сессии |

## §4. На какие секции смотреть в логе

🔴 **Здесь начинается твоя часть работы.** Я не видел содержимого лога и
увидеть не могу — ниже адреса, а не пересказ найденного.

| Что ищешь | Где искать |
|---|---|
| **системный промпт целиком** | тело первого запроса прогона: самый большой блок в начале, до первого сообщения пользователя |
| **содержимое прочитанных файлов** | категория `file`; в `.jsonl` — записи `type: attachment` и `toolUseResult` после каждого `Read` |
| **вывод терминала** | `toolUseResult` записи, соответствующей вызову `Bash` |
| **сетевой слой** | категория `api`: адрес, заголовки, размер тела, повторы |
| **что ушло «на провод»** | поля `wireIngestContext`, `wireToolInputs` |
| **срабатывания хуков** | категория `hooks` — видно, что заблокировано и чем |
| **обращения к классификатору** | `serverClassifierRequest` / `serverClassifierContext` |
| **продуктовая аналитика** | категория `1p`; отключается фильтром `!1p` |

**Полезные приёмы разбора** (выполняешь ты, у себя):

```bash
grep -n "system" "$HOME/Documents/NOT FOR CLAUDE/claude-debug-session.log" | head
grep -c "api" "$HOME/Documents/NOT FOR CLAUDE/claude-debug-session.log"
```

## §5. Что этот аудит НЕ закрывает — названо прямо

1. **Отладочный лог показывает клиента, а не сервер.** Что происходит
   с данными после приёма, из него не видно и видно быть не может.
   Это вопрос к политике провайдера (`81-claude-code-privacy-and-billing.md`),
   а не к логу.
2. **Телеметрия продукта (`1p`) — отдельный канал** от основного API.
   Он виден в логе и глушится фильтром `!1p`, но его **состав** нужно
   смотреть глазами: список полей меняется с версиями клиента.
3. **Замер сделан для версии 2.1.284.** Набор полей `.jsonl` и категорий
   отладки — свойство версии, не константа. После обновления клиента разбор
   §2 нужно прогнать заново: команда для этого приведена там же.
4. **3.4 ГБ стенограмм лежат на диске без срока хранения.** Это отдельный
   вопрос — не «что уходит», а «что остаётся». Решение по сроку и чистке
   за владельцем; ассистент их не удаляет.
